# Installer, signing and update research for Tabbi

Researched 2026-10-02, refreshed 2026-10-05.
Target: Tabbi, a SwiftPM-built macOS notch app (no Xcode project), macOS 14+, Apple Silicon and Intel.
Items marked "verified locally" were run on the maintainer's machine (macOS 26.6, Swift 6.3.3).
Items marked "inference" are judgment, not a quoted source.
Older sources call the app NotchDeck or StudyNotch; both mean Tabbi (StudyNotch is now the Med School kit).

## Decisions for Tabbi

1. Signed and notarized builds with a Developer ID are the primary path.
   The maintainer has a Developer ID, so users download the DMG, drag Tabbi to Applications and open it, with no Gatekeeper workaround.
   Ad-hoc signing stays as a documented fallback for contributors without an Apple Developer Program membership (`--adhoc`).
2. Build the DMG with `dmgbuild` (Python, headless, CI safe) using a 660x400 window, 128 pt icons at (150, 180) and (510, 180), and a two-page HiDPI TIFF background, like Boring Notch.
3. Ship Sparkle 2 (2.10.0, the latest release as of 2026-10-05) with EdDSA signing, archives on GitHub Releases and the appcast generated by the release script.
4. Build universal binaries with `swift build -c release --arch arm64 --arch x86_64`.
5. Use `SMAppService.mainApp` for launch at login and a small in-house "Move to Applications" prompt that handles App Translocation.
6. Target the official `homebrew/cask` once notarized builds ship, and keep a project tap (`ethanwchen/homebrew-tap`) as a fallback.

### Background art spec

- Author at the window size in points (660x400) and at 2x (1320x800).
- Combine into one multi-page TIFF: `tiffutil -cathidpicheck background.png background@2x.png -out background.tiff`.
  The 1x page must be 72 dpi and the 2x page 144 dpi.
  Source: https://github.com/LinusU/node-appdmg (README, "Retina background")
- Keep icon centers at least 100 pt from the edges for a 128 pt icon; Finder draws labels about 20 pt below the icon.
- Draw a soft arrow from the app to Applications; keep text away from the bottom edge, since Finder may resize the window.
- The background is a static bitmap while Finder chrome follows the system appearance, so pick a palette that reads in both light and dark mode (inference).
  For Tabbi that means the hardware-black notch palette from `Theme.Palette`, with the app's accent glow, so the DMG looks like the app.
- Rendering the art programmatically (a Swift script with AppKit/Core Graphics, like `scripts/make-icon.swift`) keeps it reproducible and reviewable in git, with no binary design files.

### Compression and filesystem

- Sparkle docs: "APFS formatted images that use lzfse compression are recommended for decent decompression speed".
  Source: https://sparkle-project.org/documentation/publishing/
- `ULFO` (lzfse) needs macOS 10.11+, fine for a macOS 14 floor; `ULMO` (lzma) is smaller but slower to open and needs macOS 10.15+.
  Pick by measured size; both work on macOS 14.

## 2. Gatekeeper and notarization on macOS 14 through 26

### What changed

- Apple, August 2024: "In macOS Sequoia, users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security to review security information for software before allowing it to run."
  Source: https://developer.apple.com/news/?id=saqachfa
- So on macOS 15 and 26, right-click > Open does NOT bypass the first-launch block for quarantined, non-notarized apps.
  On macOS 14 Sonoma, right-click > Open still works.
- Apple's current user flow: open the app once (it is blocked), then "Open System Settings. Click Privacy & Security, scroll down, and click the Open Anyway button to confirm your intent to open or install the app. The warning prompt reappears and, if you're absolutely sure that you want to open the app anyway, you can click Open." After that "The app is now saved as an exception to your security settings".
  Source: https://support.apple.com/en-us/102445
- Users report that the Open Anyway button disappears about an hour after the blocked launch attempt, and an admin password is requested.
  Source: https://www.osnews.com/story/141055/bug-or-intentional-macos-15-1-completely-removes-ability-to-launch-unsigned-applications/
  The same article's claim that 15.1 "completely removes" the ability does not hold; the Open Anyway flow still works per Apple's support page and Eclectic Light.
- Eclectic Light: quarantine is the trigger.
  Ad-hoc signed apps without the `com.apple.quarantine` attribute run without prompts; quarantined un-notarized apps need the per-app Privacy & Security exception.
  Sources:
  https://eclecticlight.co/2024/08/10/gatekeeper-and-notarization-in-sequoia/
  https://eclecticlight.co/2024/10/01/living-without-notarization/
- Apple Silicon will not run native arm64 code without at least an ad-hoc signature.
  The linker ad-hoc signs automatically, but editing the bundle (Info.plist, resources) after linking requires re-signing the whole bundle, or users see "is damaged and can't be opened".
- macOS 26 Tahoe no longer rescans notarized apps with XProtect at first launch, so a notarized first launch is faster.
  Source: https://eclecticlight.co/2025/10/13/is-tahoe-quicker-to-launch-apps-first-time/
- macOS 26 is the last release supporting Intel Macs, so keep the x86_64 slice for the life of the macOS 14 to 26 support window.
  Source: https://brew.sh/2025/11/12/homebrew-5.0.0/

### What users see

| Build | macOS 14 | macOS 15 and 26 |
|---|---|---|
| Developer ID, notarized, stapled | One dialog: "Tabbi is an app downloaded from the Internet. Are you sure you want to open it?" with Open. | Same. |
| Ad-hoc signed, quarantined | "Apple cannot check it for malicious software." Right-click > Open > Open works. | "Tabbi Not Opened. Apple could not verify Tabbi is free of malware" with only Done and Move to Trash. The user must go to System Settings > Privacy & Security > Open Anyway soon after the attempt, authenticate, then click Open in a second dialog. |
| Signature broken or missing on arm64 | "Tabbi is damaged and can't be opened." | Same. Only re-signing or `xattr -dr com.apple.quarantine` helps. |

Boring Notch, which is unsigned, documents both paths in its README: `xattr -dr com.apple.quarantine "/Applications/Boring Notch.app"` or System Settings > Privacy & Security > Open Anyway.
Source: https://github.com/TheBoredTeam/boring.notch

How to guide users kindly when they hit the ad-hoc path (inference):
say plainly that the app is safe but not reviewed by Apple, show the exact two screens with numbered steps, mention that Open Anyway only appears for a while after the first attempt, and keep the Terminal command as a last resort for people who are comfortable with it.
With a Developer ID none of this is needed, which is the real fix.

### Notarization steps (Developer ID path)

```sh
# One time on the maintainer's Mac: store credentials in the login keychain.
# notarytool prompts for the app-specific password; scripts never see it.
xcrun notarytool store-credentials notchdeck \
  --apple-id you@example.com --team-id TEAMID
# (or --key AuthKey_XXXX.p8 --key-id XXXX --issuer <issuer-uuid> for an App Store Connect API key, preferred in CI)

# Find the signing identity.
security find-identity -v -p codesigning   # "Developer ID Application: Name (TEAMID)"

# Sign inside-out: nested frameworks, XPC services and helpers first, then the app. No --deep.
codesign --force --timestamp --options runtime \
  --entitlements packaging/Tabbi.entitlements \
  --sign "Developer ID Application: Name (TEAMID)" build/Tabbi.app
codesign --verify --strict --verbose=2 build/Tabbi.app

# Notarize the app (as a zip) and staple it, then build, sign, notarize and staple the DMG.
ditto -c -k --sequesterRsrc --keepParent build/Tabbi.app build/Tabbi.zip
xcrun notarytool submit build/Tabbi.zip --keychain-profile notchdeck --wait
xcrun stapler staple build/Tabbi.app
dmgbuild -s packaging/dmg/settings.py "Tabbi" build/Tabbi.dmg
codesign --timestamp --sign "Developer ID Application: Name (TEAMID)" build/Tabbi.dmg
xcrun notarytool submit build/Tabbi.dmg --keychain-profile notchdeck --wait
xcrun stapler staple build/Tabbi.dmg
spctl --assess --type execute -vvv build/Tabbi.app
spctl --assess --type open --context context:primary-signature -vvv build/Tabbi.dmg
# On failure: xcrun notarytool log <submission-id> --keychain-profile notchdeck
```

A zip cannot be stapled; staple the `.app` and the `.dmg`.
Stats uses exactly `notarytool submit --keychain-profile ... --wait`, `stapler staple`, `spctl -a -t exec -vvv` (https://github.com/exelban/stats/blob/master/Makefile).
The keychain profile name `notchdeck` predates the rename and is kept so the maintainer's stored credentials keep working.
Scripts must never read, print or store the credentials themselves; `--keychain-profile` keeps them in the keychain.

### Entitlements under the Hardened Runtime

- The Hardened Runtime is required for notarization.
- To send Apple Events (Tabbi scripts Spotify and Music through `NSAppleScript`) under the Hardened Runtime, add `com.apple.security.automation.apple-events = true` and keep `NSAppleEventsUsageDescription` in Info.plist.
  Without the entitlement the TCC prompt never appears and events fail with `-1743` (`errAEEventNotPermitted`).
  Sources:
  https://developer.apple.com/documentation/security/hardened-runtime
  https://developer.apple.com/forums/thread/697470
- The Hardened Runtime also gates personal-information resources.
  Tabbi reads and writes calendar events with EventKit (Today, Plan my day), so it also needs `com.apple.security.personal-information.calendars = true` alongside `NSCalendarsFullAccessUsageDescription`.
  Source: https://developer.apple.com/documentation/security/hardened-runtime ("Resource Access")
- Tabbi stays non-sandboxed (it scripts other apps, runs the local `claude` CLI and reads system state), so it needs no sandbox entitlements and Sparkle needs no XPC configuration.
- Minimal entitlements file:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>com.apple.security.automation.apple-events</key><true/>
  <key>com.apple.security.personal-information.calendars</key><true/>
</dict></plist>
```

### TCC grants and updates

- TCC keys Automation and Calendar grants on the app's designated requirement.
  For Developer ID apps that is the team ID plus the bundle ID, so grants survive updates.
- For ad-hoc apps the designated requirement is the cdhash, so each new build looks like a new app to TCC and users are likely asked again after every update (inference until tested; the result of a local test belongs in `docs/install.md`).

## 3. Sparkle 2 with SwiftPM

Latest release: 2.10.0 (checked with the GitHub API on 2026-10-05).

### Why a dependency

Tabbi has a no-third-party-dependencies rule unless there is a strong reason.
Sparkle is that reason: secure in-place updates need EdDSA signature checks, a privileged-free installer that swaps the bundle while the app quits and relaunches, quarantine handling, phased rollouts and delta support.
Every app in the table above that updates itself uses Sparkle or its own long-maintained updater; writing one in-house would be a security-sensitive project of its own.
Sparkle is MIT licensed, has been maintained since 2006 and is distributed as a binary XCFramework through SwiftPM.

### Integration

- Package: `.package(url: "https://github.com/sparkle-project/Sparkle", from: "2.10.0")`, product `Sparkle`.
- With SwiftPM the CLI tools live in `.build/artifacts/sparkle/Sparkle/bin/` (`generate_keys`, `generate_appcast`, `sign_update`, `BinaryDelta`).
  Source: https://sparkle-project.org/documentation/
- When hand-assembling the `.app` from `swift build` output, copy `Sparkle.framework` into `Contents/Frameworks/`, make sure the executable has an `@executable_path/../Frameworks` (or `@loader_path/../Frameworks`) rpath, and sign Sparkle's pieces individually (below).
- Info.plist keys: `SUFeedURL`, `SUPublicEDKey`, a monotonically increasing `CFBundleVersion`, optionally `SUEnableAutomaticChecks` and `SUScheduledCheckInterval` (seconds, default 86400).
- Code: `SPUStandardUpdaterController(startingUpdater: true, updaterDelegate: nil, userDriverDelegate: nil)` and a "Check for Updates..." control wired to `checkForUpdates(_:)`.
  Tabbi has no menu bar (`LSUIElement`), so the control goes in Settings and in the notch's context menu next to Quit.
- In demo and snapshot runs, and in builds without a feed URL (`swift run`), the updater must not start, so no network happens there.

### EdDSA keys

```sh
.build/artifacts/sparkle/Sparkle/bin/generate_keys                          # creates the key in the login keychain, prints SUPublicEDKey
.build/artifacts/sparkle/Sparkle/bin/generate_keys -p                       # print the existing public key
.build/artifacts/sparkle/Sparkle/bin/generate_keys -x sparkle_private.key   # export, for a CI secret
.build/artifacts/sparkle/Sparkle/bin/generate_keys -f sparkle_private.key   # import on another Mac
```

Flags verified locally from `generate_keys --help`, Sparkle 2.10.0.
Store the exported key as a GitHub Actions secret and delete the file; never commit it.
The public key is not secret and goes in the committed Info.plist.

### Appcast generation

`generate_appcast` scans a folder of archives and writes or updates `appcast.xml`, deltas and signatures.
Release notes come from same-named `.html`, `.md` or `.txt` files; it infers the minimum OS and architectures from the bundle.
Useful flags (verified locally from `generate_appcast --help`): `--ed-key-file -` (read the key from stdin), `--download-url-prefix <url>`, `--release-notes-url-prefix`, `--embed-release-notes`, `--channel <name>`, `--maximum-deltas`, `--maximum-versions`, `--phased-rollout-interval`, `--critical-update-version`, `--auto-prune-update-files`, `-o <output>`.
`-s <key>` is deprecated.
Without `--ed-key-file` it reads the key from the login keychain, which is what a local release on the maintainer's Mac uses.

```sh
mkdir -p dist && cp build/Tabbi-1.2.0.dmg dist/ && cp notes/1.2.0.md dist/Tabbi-1.2.0.md
printf '%s' "$SPARKLE_PRIVATE_KEY" | .build/artifacts/sparkle/Sparkle/bin/generate_appcast \
  --ed-key-file - \
  --download-url-prefix "https://github.com/OWNER/REPO/releases/download/v1.2.0/" \
  --embed-release-notes --maximum-deltas 0 -o appcast.xml dist/
gh release create v1.2.0 dist/Tabbi-1.2.0.dmg --notes-file notes/1.2.0.md
```

Boring Notch's pipeline does exactly this: `printf '%s' "$SPARKLE_PRIVATE_KEY" | generate_appcast ...`, uploads the DMG to the GitHub release, then commits `updater/appcast.xml` to `main`, with separate stable and beta channels.
Source: https://github.com/TheBoredTeam/boring.notch/blob/main/.github/workflows/release.yml

Hosting:
- GitHub Releases asset URLs per tag are stable; use `--download-url-prefix` per release.
- The feed must be HTTPS (ATS).
  `https://github.com/OWNER/REPO/releases/latest/download/appcast.xml` (uploaded as a release asset) works while the repo is public and keeps the appcast out of git history; GitHub Pages or a raw URL on `main` also work.
  While the repository is private, none of these URLs are reachable by users, so updates only go live at public launch (inference from GitHub's access rules).
- Deltas are of little use for DMGs on GitHub; `--maximum-deltas 0` keeps the pipeline simple (inference).
- Archive formats Sparkle supports: zip (`ditto -c -k --sequesterRsrc --keepParent`), DMG, tar.xz and AAR (2.7+); not `.pkg` through `generate_appcast`.
  Source: https://sparkle-project.org/documentation/publishing/
- Release notes: generate them from git history (conventional commit subjects since the previous tag) into the `.md` file beside the archive; never hand-edit `CHANGELOG.md`.

### Signing Sparkle for notarization (no Xcode archive)

From Sparkle's docs, without `--deep`:

```sh
codesign -f -s "$ID" -o runtime Sparkle.framework/Versions/B/XPCServices/Installer.xpc
codesign -f -s "$ID" -o runtime --preserve-metadata=entitlements Sparkle.framework/Versions/B/XPCServices/Downloader.xpc
codesign -f -s "$ID" -o runtime Sparkle.framework/Versions/B/Autoupdate
codesign -f -s "$ID" -o runtime Sparkle.framework/Versions/B/Updater.app
codesign -f -s "$ID" -o runtime Sparkle.framework
```

Source: https://sparkle-project.org/documentation/sandboxing/#code-signing
Add `--timestamp` to each for notarization.
Library Validation (part of the Hardened Runtime) requires the framework and the app to share a team ID, so an ad-hoc fallback build signs without `--options runtime`.

### Sparkle and ad-hoc signing

- EdDSA protects update integrity independently of Apple code signing, so Sparkle works for an ad-hoc app too.
- Sparkle clears quarantine on the extracted update, so the one-time Open Anyway on first install is the only Gatekeeper hurdle (inference from Sparkle's quarantine handling; verify end to end).
- Sparkle refuses to update an app running from a translocated or read-only location, which is another reason to move the app to /Applications on first launch.
- Sparkle's prebuilt helpers ship ad-hoc signed and must be re-signed with the Developer ID for notarization.

## 4. Homebrew casks

- Homebrew 5.0.0 (2025-11-12): "Casks without codesigning are deprecated. We will disable all Homebrew/homebrew-cask casks that fail Gatekeeper checks in September 2026."
  Also: "--no-quarantine and --quarantine flags have been deprecated as Homebrew does not wish to easily provide circumvention to macOS security features."
  Intel Macs move to Tier 3 in September 2026, and Homebrew will not run on Intel from September 2027.
  Source: https://brew.sh/2025/11/12/homebrew-5.0.0/
- The cutoff was 2026-09-01; deprecated casks now print "will be disabled on 2026-09-01" (for example CopyQ).
  Sources:
  https://github.com/hluk/CopyQ/issues/3498
  https://github.com/ivoronin/TomatoBar/issues/102
- Acceptable Casks: "apps, installers and other executable artefacts that Gatekeeper can assess must pass Homebrew's Gatekeeper checks and must not require System Integrity Protection or Gatekeeper to be disabled or bypassed."
  Source: https://docs.brew.sh/Acceptable-Casks
- So only a Developer ID signed and notarized Tabbi can go into `homebrew/cask`; it also has notability requirements (stars, forks or watchers) that a newly public repo may not meet yet, which is why the tap stays as a fallback.
- Third-party taps are not reviewed by homebrew-cask.
  Boring Notch's tap cask uses `depends_on macos: :sonoma`, `auto_updates true`, `uninstall quit: "<bundle id>"`, `zap trash: [...]` and a `postflight` that strips quarantine.
  That postflight is exactly the circumvention Homebrew is moving away from, so Tabbi's cask must not do it (a notarized build does not need it).
  Source: https://github.com/TheBoredTeam/boring.notch/blob/main/.github/workflows/release.yml
- For a Sparkle-updating app set `auto_updates true` so `brew upgrade` does not fight Sparkle, and add `livecheck` with `strategy :sparkle` pointing at the appcast.

## 5. Move to Applications, single instance and launch at login

### Move to Applications

- LetsMove (Objective-C, `potionfactory/LetsMove`) and AppMover (Swift, `OskarGroth/AppMover`) were last pushed in 2022-06.
  Both still work as references but are effectively unmaintained.
  Sources: https://github.com/potionfactory/LetsMove , https://github.com/OskarGroth/AppMover , https://christiantietze.de/posts/2020/01/appmover-swift/
- Why it matters: Gatekeeper App Translocation runs quarantined apps launched from Downloads or a DMG from a random read-only path, which breaks Sparkle, `SMAppService` login items and relative resource paths.
- In-house pattern (about 100 lines of Swift, inference):
  1. On launch, if `Bundle.main.bundleURL` is not under `/Applications` or `~/Applications`, or its path contains `/AppTranslocation/`, show a one-time alert ("Move Tabbi to your Applications folder?" with Move and Not Now, plus "Don't ask again").
  2. If translocated, resolve the original path (LetsMove uses the private `SecTranslocateCreateOriginalPathForURL` through `dlsym`); if it is on a mounted disk image, copy from there.
  3. Copy with `FileManager.copyItem` to `/Applications/Tabbi.app`, replacing an existing copy after quitting it; if `/Applications` is not writable, fall back to `~/Applications`.
  4. Relaunch with `NSWorkspace.shared.openApplication(at:configuration:)` and quit; trash the original if it was in Downloads; if launched from a disk image, eject it.
  5. Skip entirely when running from `.build/` (`swift run`), in demo and snapshot runs, and in debug builds.
- The decision logic (where am I, should I ask, where should the copy go) is pure and belongs in `TabbiKitCore` with unit tests; only the alert and file moves live in the app.

### Another copy is running

- `NSRunningApplication.runningApplications(withBundleIdentifier:)` lists other instances; when one exists (and it is not this process), activate it and quit the new one.
- After a move, the relaunched copy must wait for the old process to exit (pass its pid, or retry briefly) so it does not see itself as the duplicate.

### Launch at login

- `SMAppService.mainApp` (macOS 13+): `register()`, `unregister()`, read `status` (`.enabled`, `.notRegistered`, `.requiresApproval`, `.notFound`), and `SMAppService.openSystemSettingsLoginItems()` when status is `.requiresApproval`.
  Source: https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp
- Tabbi turns it on by default on first launch from /Applications (the product brief asks for that) and shows a visible toggle in Settings; macOS also posts a "Login item added" notification, so the user is never surprised.
- Always derive the toggle from `status` (re-read when the app becomes active or Settings opens), because users can flip it in System Settings > General > Login Items.
- Register only after the app is in /Applications; a login item registered from a translocated path points at a path that will not exist next boot (inference).

## 6. Universal binary builds

Verified locally (Swift 6.3.3, macOS 26):

```sh
swift build -c release --arch arm64 --arch x86_64
swift build -c release --arch arm64 --arch x86_64 --show-bin-path   # .build/apple/Products/Release
lipo -archs .build/apple/Products/Release/Tabbi                     # x86_64 arm64
```

- Two `--arch` flags switch SwiftPM to the XCBuild backend; outputs go to `.build/apple/Products/Release/` instead of `.build/release/`.
- Pitfalls: `-Xcc`, `-Xswiftc` and `-Xlinker` flags may be ignored in multi-arch mode, and there were `Bundle.module` resource bugs in this mode (Swift 5.9).
  Sources:
  https://forums.swift.org/t/unable-to-compile-universal-binary-for-command-line-swift-package/53948
  https://forums.swift.org/t/swift-5-9-type-bundle-has-no-member-module-when-building-universal-binary-via-swift-build-command/66882

- Fallback that always works: build each architecture separately and merge with `lipo -create`.
- Resource bundles are architecture independent; copy one into `Contents/Resources/`.
- Strip the release binary (`strip -x`, or `-Xlinker -dead_strip` plus `-Xswiftc -gnone` style settings) before signing to keep the bundle lean, and sign after `lipo` and after any Info.plist edit.
- Keep `LSMinimumSystemVersion` at `14.0`; Sparkle reads it and the architecture slices into the appcast.

## 7. Plan for this repository

- `packaging/`: entitlements, `dmgbuild` settings and pinned requirements, the DMG background renderer and the Homebrew cask templates.
- `scripts/make-dmg.sh <edition>`: renders the background, builds the DMG, signs, notarizes and staples it when a Developer ID is set up.
- `scripts/release.sh`: universal build, strip, assemble, sign inside-out (Developer ID by default, `--adhoc` fallback), notarize, staple, DMG, appcast, release notes from git and checksums; fails with a friendly two-step setup message when the identity or the `notchdeck` notary profile is missing.
- `.github/workflows/release.yml`: `workflow_dispatch` only while the repo is private.
- App: an install-hygiene folder (move to Applications, single instance, launch at login) that hands off to onboarding through one small call, and a Sparkle updater with "Check for Updates..." in Settings and the notch menu.
- `docs/install.md`: the non-technical guide, with rendered images and an uninstall section.
