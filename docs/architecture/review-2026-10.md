## Summary

The foundations are good.
`ModuleID` is open, `ModuleLifecycle`, `ModuleLayout`, `ProviderSnapshot` and the kit model are pure values in `NotchKitCore` with solid tests, and the build is clean.
But the "a new vertical is a kit plus a module, no new plumbing" claim does not hold yet.
A LeetCode module that feeds Today and the ticker today needs edits in about eight shared files, and the five parallel agents will all collide on `AppServices.swift`.
The biggest gaps are: a static built-in catalog that the registry does not actually drive, no module context (dependencies come from a god object and singletons), a closed ticker enum that ignores provider progress, a provider schema shaped around Today's `FocusTimer`, and no activity/event channel for the gamification and insights agents that come later.

Severity key: **Blocker** (fix before or alongside the current agent wave, or the vision breaks), **Should-fix** (fix before the later agents or before community kits exist), **Nice-to-have**.

## Walkthrough: adding a LeetCode vertical today

Goal: a `leetcode` module whose daily problem shows in Today and in the closed-notch ticker, shipped with a `tech` kit.

1. Write `Modules/LeetCode/LeetCodeModule.swift` conforming to `NotchModule`. Fine, self-contained.
2. Give it a descriptor. Every module reads its descriptor from `ModuleCatalog.builtIn` (for example `AnkiModule.swift:8`), and `ModuleLayout.init` drops any id not in `ModuleCatalog.builtIn` (`ModuleLayout.swift:26-28`, default argument). Tab titles, symbols and accents also resolve through `ModuleID.descriptor`, which reads `builtIn` (`ModuleID.swift:28`, `Theme.swift:25-27`). So you must edit `ModuleCatalog.swift:42-66` (shared) and the exact-order test `ModuleAndCLITests.swift` (`testBuiltInKeepsTheShippedTabOrder`). `ModuleRegistry.catalog` (`NotchModule.swift:60,73`) is computed but never used.
3. Register it and its store in `AppServices.swift:14-47` (shared), because modules get no dependencies except what `AppServices` passes.
4. Today: return `ModuleProvision(progress: [...])` or `tasks`. This works with no Today edits (`SharedTodayItem.swift:34`, `PlannerList.swift:208-256`). Good.
5. Ticker: `TickerSources` has fixed fields and no progress (`TickerItem.swift:90-118`), `TickerKind` is a closed enum (`TickerItem.swift:4`) whose click target is hard-wired (`TickerItem.swift:25-31`), and `TickerStore` reads Spotify and Claude Usage stores directly (`TickerStore.swift:34-44`). Showing "LeetCode: 1 problem left" means editing `TickerKind`, `TickerItem`, `TickerSources`, `NotchPreview.swift`, `NotchPreviewLayout.swift`, `SnapshotRenderer.swift:131-135`, `KitValidation.swift` and docs. Provided tasks only surface as the generic `tasks` count, which is hidden when Today is off and always opens Today.
6. Kit defaults for the module (say, difficulty): `moduleSettings` can carry them, but nothing calls the module when a kit is applied. The only hook is `settings.kitApplied` in `AppServices.swift:63-73` (shared), and `KitIssue` cannot report problems in a module's own section.
7. Network disclosure: `ModulePermission` has no network case (`ModuleDescriptor.swift:24-41`), so the LeetCode (or Party) module cannot declare it, and the enum is closed.
8. Category: `ModuleCategory` is a closed enum (`ModuleDescriptor.swift:2-20`) with no `tech` or `law`.
9. Bundled kit: add JSON plus an entry in `KitLibrary.bundledIDs` (`KitLibrary.swift:7`). Acceptable, but could be discovered from the bundle.

Net: steps 2, 3, 5, 6, 7 and 8 are shared-file edits. The design intent (ROADMAP "if a vertical needs changes to shared code, the provider protocols are missing something") is right; the protocols are missing a few things listed below.

## Findings

### Blocker

**B1. The built-in catalog, not the registry, is the source of truth for modules.**
Files: `ModuleCatalog.swift:42-66`, `ModuleID.swift:28`, `ModuleLayout.swift:26,40`, `KitApplication.swift:32`, `AppSettings.swift:71,84`, `KitValidation.swift:77`, `KitManifest.swift:81`, `Theme.swift:26`, every `*Module.swift` descriptor line, `NotchModule.swift:60,73` (unused `catalog`).
Every new module edits one shared static list in the pure core, and the descriptor is defined in one place while the module that owns it lives in another.
Fix: make each module own its descriptor (`static let descriptor = ModuleDescriptor(...)` in its folder) and build the catalog from the registry at launch.
Inject that catalog into `SettingsRepository`, `SettingsStore`, `AppSettings.apply`, `KitManifest.issues/layout` and the tab bar instead of defaulting to `.builtIn` (remove the default arguments so a missed call site fails to compile).
Replace `ModuleID.descriptor`/`title`/`symbol` and `Theme.Palette.accent(for: ModuleID)` with lookups through an injected catalog (an environment value in SwiftUI).
Keep `ModuleCatalog.builtIn` only as a test fixture, and turn the order test into "registry ids are unique and every bundled kit resolves".

**B2. `AppServices` is the composition root, the store owner and the event wiring: all five agents must edit it.**
Files: `AppServices.swift:6-8` ("add new stores here"), `:14-47`, `:63-73`; `AGENTS.md` ("a store, owned by AppServices"); panels pull the whole object from the environment (`PlannerPanel.swift:13`, `FocusPanel.swift:10`, `ModuleViews.swift:28`); singletons `FocusController.shared` (`FocusController.swift:24`, used from `AppServices.swift:66`, `FocusStore.swift:21`, `SettingsPanes.swift:159`).
Study, Anki, Today, pet coach/Closet and Party will each add a stored property, change a constructor in the `ModuleRegistry([...])` literal, and probably add a `kitApplied` branch, producing five-way merge conflicts in the same 30 lines.
Fix: introduce a `ModuleContext` passed to every module's init, holding the shared services a module may use: `providers` (read-only snapshot publisher), `settings` read access, kit application events, a per-module storage handle (see S5), `isDemo`/`isSnapshot`, the edition, and a `FocusService` protocol instead of `FocusController.shared`.
Let each module construct and own its store from the context, so `AppServices` shrinks to `ModuleRegistry(MyModules.all.map { $0.init(context:) })`.
Put that list in its own file (`Modules/ModuleList.swift`), one line per module, sorted, so concurrent additions are trivially mergeable.
Stop injecting `AppServices` into panels; give panels what they need through the module.
Do this in a small PR now, before the five agents get far, and tell them to rebase.

**B3. The ticker is a closed enum that ignores provider progress and is wired to specific stores.**
Files: `TickerItem.swift:4-31`, `:57-71`, `:90-118`; `TickerStore.swift:34-44`; `NotchPreview.swift:40-72`; `NotchPreviewLayout.swift:23-58`; `SnapshotRenderer.swift:131-135`; `AppSettings.swift:62-64`.
ROADMAP says the ticker reads every provider; in fact it reads events, a focus timer, a task count, plus Spotify and Claude Usage directly.
`ProgressItem` (Anki due cards, the LeetCode daily) never reaches it, a focus timer from Study opens Today on click, and every ticker kind is hidden when Today is disabled because `TickerKind.module` is `.planner`.
Fix: add a generic provider role, for example `ModuleProvision.highlights: [TickerHighlight]` where a highlight carries `source`, `id`, `symbol`, `text`, `priority`, optional `countdownTo` and `pinned`, rendered by one generic preview view.
Keep the special renderers (music wings, meeting) but make Now Playing and Claude Usage provide through their modules like everyone else, and derive the click target from `source`.
Settings then toggles previews per source module instead of per `TickerKind`, and the kit `ticker` field lists module ids.

**B4. `ModuleProvision.focus` is Today's `FocusTimer`, but Study ships a different engine (`StudySession`).**
Files: `ModuleProvision.swift:71,99,121-126`; `TickerItem.swift:61`; `docs/studynotch/core.md:127-162`.
The Study agent must either convert a `StudySession` into a `FocusTimer` (lossy: flowtime, sprint card goals, review phases) or edit the shared provider type, and the Today/Focus timer and the Study timer will both claim the ticker.
Fix: replace it with a neutral `FocusActivity` value (`source`, phase label and kind focus/break, `endsAt` or elapsed, `isRunning`, optional progress) that both engines map into, and decide policy for two concurrent timers (for example the most recently started running one wins, and Study offers to stop the Pomodoro when it starts).

**B5. `ProviderHub` traps if any module publishes off the main thread.**
File: `ProviderHub.swift:37-39` (`MainActor.assumeIsolated` inside `sink`); same pattern in `PlannerStore.swift:81`, `AppServices.swift:65`.
The Anki module will poll AnkiConnect with `URLSession` and async code, and Party will use the network; a `Combine` publisher fed from those (for example `dataTaskPublisher` or a `PassthroughSubject` sent from a task) emits on a background queue and crashes the app at runtime, which no test catches because the hub lives in the untested executable.
Fix: in the hub, hop explicitly (`if Thread.isMainThread { MainActor.assumeIsolated { ... } } else { DispatchQueue.main.async { ... } }`), or declare `provision` as a main-actor-isolated `AsyncStream`/`@Published` property so the compiler enforces it.
Document the rule on `NotchModule.provision`, and add a test that a background emission is delivered.

### Should-fix

**S1. No activity/event channel or history for gamification, insights and the pet coach.**
Files: `ModuleProvision.swift` (current-state snapshot only); `StudySession` `takeLog()` ("until the app collects them", `core.md`); `FocusStore.swift:24` keeps its own `FocusSessionLog` in UserDefaults.
XP, streaks, insights and pet moods all need "what happened" (focus phase completed, task done, N cards reviewed, problem solved), not just "what is true now".
Without a shared channel, those later agents will reach into `StudyStore`, `FocusStore` and `PlannerStore` directly, which AGENTS.md forbids.
Fix: add an append-only `ActivityRecord` (`source`, `kind` as an open string id, `start`, `end`, `quantity`, `unit`, metadata) in `NotchKitCore`, a `NotchModule.activity` publisher, and one `ActivityLog` store (daily JSONL files, versioned) that gamification and insights read.
Migrate `FocusSessionLog` and `StudyPhaseRecord` onto it.

**S2. Vertical-specific fields are baked into the kit schema and its validator.**
Files: `KitManifest.swift:131-208` (`studyMethods`, `studyMethod`, `focusSounds`, `pet` typed in core), `KitValidation.swift:30-50,92-98`.
Each vertical setting means editing the core struct, the closed `KitIssue` enum and docs; `moduleSettings` exists but cannot be validated or applied by the module.
Fix, while format 1 is pre-community: move per-module defaults under `moduleSettings` (for example `"study": {"methods": [...]}`, `"closet": {"pet": {...}}`, `"focus": {"sounds": [...]}`), keep only cross-cutting fields (`ticker`, `theme`) at the top, and add two module hooks: `validateKitSettings(_ KitValue) -> [String]` (warnings surfaced as `KitIssue.module(id, message)`) and `applyKit(_ KitValue?, answers:)` called by the registry on `kitApplied`.
Support the current keys as aliases for one release, then drop them.

**S3. Kit import is not safe enough for community sharing.**
Files: `ImportedKitStore.swift:37-52`, `SettingsPanes.swift:240-266`, `KitValidation.swift:69-74`, `AppSettings.swift:71-79`, `PlannerStore.swift:109`.
- Import immediately switches kits when there are no questions, replacing the user's tabs and previews and adding starter tasks, with no preview of what will change, which permissions the new tabs will prompt for, and no undo.
- Importing a file whose id matches an earlier import silently overwrites it.
- Reserved ids are only today's bundled ids; when a future release bundles `law`, a user's imported `law` is silently shadowed (`KitLibrary.installed`, `ImportedKitStore.swift:71-73`) and their active kit changes under them.
- No limits: file size, string lengths (`name`, `summary`, task titles), number of modules, questions, options and starter tasks are unbounded, so a hostile or sloppy kit can flood Today or break layout. `formatVersion` 0 or negative is accepted, answer id uniqueness and empty `options` are not checked, focus `level` outside 0...1 is silently clamped without a warning, and unknown keys inside `defaults` (typos such as `tickers`) produce no warning.
Fix: show a confirmation sheet (tabs on, permissions from descriptors, starter tasks, settings it changes) before applying, and snapshot the previous `AppSettings` for one-click undo.
Ask before replacing an imported kit with the same id.
Namespace imported ids (store as `user/<id>`, or reserve all unprefixed ids for bundled kits) so future bundled kits never collide.
Enforce caps (for example 64 KB file, 80-character names, 12 modules, 10 questions, 20 starter tasks, 120-character task titles), require `formatVersion >= 1`, and add `KitIssue.unknownField(path)` by decoding a second time into `[String: KitValue]` and diffing keys.
Write down in `docs/kits.md` that kits may never set URLs, endpoints, file paths, shell commands, Shortcuts names or anything executable, and enforce it in the module validators from S2.

**S4. Kit versioning conflates format and app capability.**
File: `KitManifest.swift:14-16`, `KitValidation.swift:70`.
`formatVersion` is the only version; a kit that needs a module from a newer app still loads and silently skips it, which is right for optional modules but wrong for a kit whose whole point is that module.
Fix: add optional `requires: { "modules": ["leetcode"] }` (refuse with a clear "needs a newer NotchDeck" message when missing) and an optional author-owned `version` string for kit updates, so re-imports can say "update Deep Work 1.2 to 1.3".

**S5. Persistence locations and edition isolation are inconsistent.**
Files: `PlannerRepository.swift:13-16` and `DayReview.swift:200-204` hardcode `Application Support/NotchDeck/...`; `ImportedKitStore.swift:18-21` uses the edition name; settings, focus and Claude usage use `UserDefaults.standard` per bundle id (`FocusStore.swift:29`, `ClaudeUsageStore.swift:32`); `NotchViewModel.swift:18,41` writes the selected tab from the shared UI library.
So a StudyNotch install shares Today's checklist and reviews with NotchDeck but not its kits, settings or focus timer, contradicting `docs/kits.md:35` and the `Edition` doc ("each edition is its own app").
Fix: one `AppStorage` service from the edition (`supportDirectory(for module: ModuleID)`, `defaults`), passed through `ModuleContext`, and a one-time migration that moves StudyNotch's planner files if they were written under `NotchDeck/`.
Decide explicitly whether editions share data; the code currently does both.

**S6. No schema versions or migration point for persisted data.**
Files: `AppSettings.swift:107-208` (per-key, no version), `FocusStore.swift:39-40` (legacy `planner.*` keys for focus data), planner and review JSON files, `ClaudeLimitsRecord`.
Also, `ModuleLayout` drops unknown ids on load and `save` rewrites the list (`AppSettings.swift:151-154,186-188`), so running an older build (or a build without a module) permanently loses that module's position and on/off state.
Fix: add a `settings.schemaVersion` key with an ordered migration list run in `SettingsRepository.load`, put a `schemaVersion` field in each JSON file, and preserve unknown module ids in the stored order (filter them only in the live layout).

**S7. App-level logic has no tests and the core is not locked to Swift 6.**
Files: `Package.swift:6,43-47`.
Fix: add a `NotchDeckTests` target depending on the executable target (SwiftPM supports `@testable import` of executables) or move `ModuleRegistry`, `ProviderHub` and `TickerStore` logic into `NotchKit`, and cover registry start/stop on enable, hub merge and background delivery (B5), kit application side effects, and Settings pane composition.
Switch `NotchKitCore` to `.swiftLanguageMode(.v6)` now (it is already clean under complete checking) so new core code from five agents cannot regress, and fix the 14 strict-concurrency warnings in `NotchDeck`/`NotchKit` before turning on Swift 6 there.

**S8. Other shared files the parallel agents will collide on.**
- `ModuleDescriptor.swift:24-41`: Party needs a network disclosure; add `.network` (with a host list in the descriptor) instead of each agent improvising.
- `SnapshotRenderer.swift`, `TickerItem.swift`, `NotchPreview*.swift`: Study's timer in the ticker (until B3 lands).
- `Theme.swift`: shared components requested by several modules; agree on owners or a `Components/` file per component.
- Pet state: pet coach and Closet both touch `NotchKitCore/Pets` (`PetSave`, `PetProfile`); assign one owner for pet persistence and have the other consume it through a provider or service.
- Study vs Focus: both are timers that drive focus sounds through `FocusController.shared`; agree on the `FocusService` boundary (B2, B4) before both agents write code.
- `AGENTS.md` and `docs/kits.md` module tables: every agent will append rows; fine, but expect conflicts.

### Nice-to-have

**N1. Silent duplicate-id handling hides agent mistakes.**
`ModuleRegistry.init` (`NotchModule.swift:64-74`) and `ModuleCatalog.init` drop a later duplicate silently.
Fix: `assertionFailure` in debug builds, plus a test that the registry has no duplicates.

**N2. Closed enums that verticals will want to extend.**
`ModuleCategory` (`ModuleDescriptor.swift:2`) and `Edition.builtIn` (`Edition.swift:44`).
Fix: make category an open `RawRepresentable` struct like `ModuleID`, and describe editions as data (a small JSON beside the kits: id, name, bundle id, default kit, icon) read by `bundle.sh` and the app, so an LSAT edition is a file, not a code change.

**N3. Bundled kit list is hand-maintained.**
`KitLibrary.swift:7`.
Fix: enumerate `Kits/Bundled/*.json` and order by an optional `pickerOrder` field, with a test that every file loads with no issues.

**N4. Demo and snapshot mode are read from the environment in 31 places.**
`grep NOTCHDECK_DEMO` shows checks scattered across stores (for example `AnkiModule.swift:17`, `FocusController.swift:55-56`, `FocusStore.swift:45`).
Fix: one `RunMode` value in `ModuleContext` (live, demo, snapshot), so new modules cannot forget it.

**N5. Provider dedupe semantics differ by role.**
`ProviderSnapshot.init` keys tasks and progress by `(source, id)` but events by `id` alone (`ModuleProvision.swift:107-120`).
Intentional for calendar events shared across modules, but undocumented; document it or key events by source plus id with an explicit cross-source merge.

**N6. `KitValue.decode` round-trips through JSON on every read.**
`KitValue.swift:43-45`.
Fine at current scale; cache decoded module settings if modules read them on hot paths.

## Docs that contradict the code

1. `docs/ROADMAP.md:17` says adding a module "never means editing another", and `:18` says "Today, Plan my day and the closed-notch ticker read every provider". The ticker ignores `progress`, and new modules must edit `ModuleCatalog.builtIn` and `AppServices` (B1, B2, B3).
2. `AGENTS.md` (shared data providers paragraph) says "The ticker reads it" as if all roles flow to the ticker; only events, focus and the open task count do.
3. `AGENTS.md` (module folders) says a module's store is "owned by AppServices", while the ownership rule says to keep changes inside `Modules/<Module>/`. These conflict for every new module with state.
4. `NotchModule.swift:8-11` says a module "is listed once in `AppServices`, so adding a module never means editing a switch in shared code", but its descriptor must also be added to `ModuleCatalog.builtIn` or the layout drops it.
5. `docs/kits.md:35` and `Edition.swift:5-10`/`ImportedKitStore.swift:16-17` say each edition keeps its own files, but planner and review data always go to `Application Support/NotchDeck` (`PlannerRepository.swift:13-16`, `DayReview.swift:200-204`).
6. `docs/kits.md:59` and `:175` say an id "can't be the id of a bundled kit"; this only holds for today's bundled ids, and a later bundled kit silently shadows an imported one with the same id.
7. `docs/kits.md:107` shows `"moduleSettings": { "anki": { "deck": "AnKing" } }`, but no module reads `moduleSettings` yet and the Anki module documents no shape; mark it as illustrative or remove it until Anki reads it.
8. `docs/kits.md:178` lists what triggers warnings but not that unknown keys inside `defaults` are silently ignored, so typos go unreported.
